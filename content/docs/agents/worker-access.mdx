title: Worker access setup
description: Connect task workers to GitHub or Forgejo, with optional Tailscale enrollment for private repositories.

Every task worker needs to reach the project's repository to fetch source and publish results. **Tailscale is optional.** A private repository on GitHub can be reachable over the internet while still requiring authentication; “private repository” does not necessarily mean “private network.”

## Availability

Automatic worker provisioning and **Settings → Tasks Mode → Worker access** are part of the **Harness Test preview**, not the public 1.28.2 release. The preview covers repository tasks launched through exe.dev and GitVM. Publishing this guide does not update your installed app.

## Choose your connection

| Where the repository is reachable | What to configure |
| --- | --- |
| GitHub or an internet-accessible Forgejo server | Set the project's repository and forge connection. Leave the Tailscale fields empty. |
| A private network the worker already reaches, including an existing VPN | Leave the Tailscale fields empty. Confirm the worker has the required DNS, routes and access rules. |
| A private Tailscale network that new workers have not joined | Configure a reusable enrollment key once, as described below. |
| A private network without Tailscale or another worker connection | Provide network access through your worker image/infrastructure, run workers inside that network, or use a reachable repository endpoint. An enrollment key is not required unless you choose Tailscale. |

The worker needs access to the repository's **SSH endpoint and HTTP(S)/Git LFS endpoints**. Access from your desktop alone does not establish access from a remote worker. xNaut checks connectivity before launching the task; it does not automatically configure other VPN products or publish a private server to the internet.

## Set up the project repository

1. Configure GitHub or Forgejo under **Settings → Tasks Mode → Forge Hosts**. The forge connection needs permission to manage repository deploy keys and create pull requests.
2. Set the destination repository in the project's settings. Use the repository for source and task results, not a local folder path.
3. Leave **Worker access** empty if the worker already reaches that repository.

Desktop Git access and worker Git access use separate credentials. If this checkout uses an SSH alias (such as `forgejo:team/repo.git`), the updated preview preserves that alias for desktop uploads and downloads when it resolves to the configured repository. It does not copy your desktop private key to a worker or use another repository mirror. You can also set the intended SSH alias clone URL explicitly in project settings.

xNaut prepares tools and a repository-specific worker deploy key, then checks Git read/write and Git LFS authorization. Network access and repository permissions are separate: a Tailscale key does not grant Git permissions. Results use a task branch and pull request. Automatic review and merging are off until the project owner enables the permissions below.

## Create the worker tag first, if using tags

Typing a tag into xNaut does **not** create it in Tailscale. Before using `tag:xnaut-worker`:

1. Open [Tailscale Access controls → Definitions → Tags](https://console.tailscale.com/admin/acls/visual/tags).
2. Select **Create tag**. In Tailscale's **Tag name** field, enter `xnaut-worker`.
3. Choose the account or group authorized to assign it under **Tag owner**, then select **Save tag**.
4. Confirm the saved list shows `tag:xnaut-worker`. Check that your network policy permits workers with that tag to reach the repository's SSH and Git LFS endpoints.

Then generate the enrollment key below using an account authorized for that tag. Tailscale's form supplies the prefix when it saves the tag; xNaut's **Worker network tags** field requires the full value `tag:xnaut-worker`.

## Create a Tailscale enrollment key

An enrollment key is a Tailscale **auth key**. It lets workers join your network without an interactive browser login. Create it in the same tailnet as your repository server, using an account allowed to generate keys.

1. Open [Tailscale Settings → Keys](https://login.tailscale.com/admin/settings/keys).
2. Select **Generate auth key**.
3. Use these settings:

| Setting | Value |
| --- | --- |
| Description | `xNAUT workers` |
| Reusable | **On**, so multiple workers can enroll |
| Pre-approved | **On** if device approval is enabled; this is what xNaut means by “preauthorized” |
| Expiration | Choose 1–90 days; replace the key before it expires |
| Ephemeral | **On** for disposable task workers; inactive devices are automatically removed |
| Tags | Prefer a dedicated worker tag whose access rules allow the repository endpoints |

4. Select **Generate key** and copy it directly into xNaut's **Tailscale enrollment key** field.
5. If the auth key already assigns the required tags, leave **Worker network tags** empty. Otherwise enter only tags that already exist and are authorized for that key, for example `tag:workers`. Include the `tag:` prefix; separate multiple tags with commas. An example tag is not created automatically. See [Tailscale tag permissions](https://tailscale.com/docs/features/tags).
6. Select **Save Tasks Mode Settings**.

See [Tailscale's auth-key documentation](https://tailscale.com/docs/features/access-control/auth-keys) for key settings and lifecycle. Never put the key in chat, task instructions or your repository.

## What happens for new workers

When the repository is already reachable, xNaut skips enrollment. Otherwise, with a configured key, it installs Tailscale if needed and attempts enrollment. The key travels over the worker's SSH connection and is removed from its temporary worker file after the attempt. Configure this once for the fleet; do not create a separate key or perform a browser login for each task.

The current preview uses the saved auth key and does not rotate it automatically. Replace it in Worker access before expiry so future workers can enroll. Already enrolled devices have a separate device-key lifecycle.

## Tasks and shared environments

The current exe.dev driver reuses one persistent VM. Each task gets a separate repository checkout and tmux session on that VM; starting a new task does not require stopping another task. The updated Harness Test preview counts this shared VM once for the environment ceiling, while concurrent-agent and daily-launch limits still apply separately. Earlier previews incorrectly counted agent/project records as separate exe.dev environments.

Reusing an environment does not mean sending a new task into another agent's active terminal. Keep active and waiting sessions intact. Retrying the same task key returns its existing launch receipt if a launch was already recorded; if setup failed before launch, there is no worker process to resume yet.

## Try a new task

Name the registered project explicitly. Replace `YOUR-PROJECT-KEY` with its key from project settings:

> For registered project YOUR-PROJECT-KEY, run a harness smoke test: create a short task report without changing application source, publish the result, and report the task branch.

When retrying a blocked attempt, include its original task key so the harness reuses the same task identity. Repository tools resolve registered project keys/names in the updated Harness Test preview; older previews require the exact absolute local source path.

The starting revision must already belong to a published source branch. Task PRs use that branch as their target, so a report-only task from a feature checkout does not silently include that feature's application changes against `main`. For a detached checkout, the preview can resolve a unique exact published branch; otherwise select the intended source branch in the project's local folder. Unpublished starting commits and ambiguous detached tips stop before launch with setup guidance.

Verify that setup completes, the task actually runs, and its report reaches the task branch and pull request. A launch receipt alone is not proof of delivery. See [Agent Harness](/docs/agents/harness) for execution and review stages.

## Automatic testing, review and project merge permission

The updated **Harness Test preview** adds **Project settings → Testing, review and merge**. Ralph and Otto are baseline agents shipped alongside NautBot; no new agent is required. Ralph now independently tests and reviews the exact task commit. His validator role remains compatible with existing release checks. Customized profiles and deliberately deleted agents are preserved.

1. Save the project's repository connection first.
2. Enable **Automatically ask Ralph to test and review task PRs** to request an isolated review worker after successful repository delivery. Normal worker access, agent concurrency and spend limits still apply.
3. Optionally check **I authorize Otto to merge passing task PRs for this project** and select **Save review permissions**. This is a separate owner agreement, off by default. Agents cannot grant it through their task tools.
4. For a PR published before this feature, select **Review** in the project's transfer list. Enabling review does not silently launch workers for legacy receipts.

For a task PR already known to this desktop, you can also ask an agent: **“Review XNAUT PR #105”**, substituting your project and PR number. The updated preview resolves the saved task receipt to its registered project and local folder, then queues the existing PR instead of creating another task. A full PR URL disambiguates duplicate numbers. A queued review is not proof that a worker started. Project permission and worker admission still apply. Saved execution receipts are local to the desktop; a fresh machine needs the original receipt/context before this shortcut can resolve that task.

The desktop app must remain running to reconcile results. Ralph's evidence is published to a separate task branch and summarized on the original PR; it does not recursively open more review PRs. If Ralph authored the task, the existing Reviewer agent provides the independent review. An unavailable reviewer or blocked launch stays visible rather than attaching to another active session.

Otto's merge stage is a deterministic desktop action under the saved project permission; it does not start an additional conversational worker. It requires all of these gates:

- A successful independent review of the exact PR and target commits, with successful tests, committed regular-file logs, no source edits by the reviewer, and no unresolved findings or coverage gaps.
- The task branch includes the current target commit. If either commit changes, update the task branch as needed and request a fresh review.
- The PR is open, ready, mergeable and belongs to the configured repository. Reported CI statuses and GitHub check runs must be complete and successful. Native forge rules and required approvals still apply.
- Branch protection prevents merging an outdated branch **and applies to administrators**. On GitHub this means required status checks with strict/up-to-date enforcement and administrator enforcement. On Forgejo it means blocking outdated branches and applying protection to administrators. xNaut does not change these repository policies for you. If it cannot verify them, merge manually after review.
- The existing deterministic change-risk score is below the human-review threshold.
- Jev's merge guard passes through the configured NautGate connection. This guard is independent of the tool-selection setting. It evaluates test coverage, scope alignment and serious unresolved risk, receiving the task report, changed file statistics, review and bounded test-log excerpts. It does not receive the entire repository or forge credentials.
- The project permission remains enabled and unchanged immediately before the merge request.

Jev supplies an additional judgment, not permission or a guarantee of correctness. The preview's initial thresholds require coverage and scope probabilities of at least 0.90 and serious-risk probability at most 0.10; they still need evaluation against real project outcomes. Missing, malformed, uncertain, failed or timed-out results stop automatic merging. The returned model, probabilities, thresholds and usage are saved in **Decisions** history and summarized on the task PR.

The merge request checks the exact head commit, never forces a merge, never deletes the branch, and never queues an unchecked future merge. Interrupted or ambiguous merge results require inspection before another attempt. A successful merge does not publish a release or bypass existing release approval.

Switching off the project agreement prevents subsequent merge requests; it cannot cancel a request already submitted to the forge. Changing the repository revokes the agreement, including when you later switch back. Review failures stay visible in the transfer list. **Retry review** only starts another attempt when the previous run is known to have stopped, and allows at most three attempts. An uncertain launch or merge outcome needs owner inspection instead of another worker.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Repository not reachable / `network_setup_required` | Confirm the URL, DNS, SSH port and worker network route. Configure optional Tailscale enrollment only if that is how your server is reached. |
| Git works in a terminal but launch fails at `ls-remote` | Use the updated Harness Test preview, which preserves matching desktop SSH aliases. Confirm the project repository and local SSH configuration target the same host, port, account and repository. |
| Invalid or rejected worker tags | Include the `tag:` prefix and check the key’s allowed tags and tailnet policy. If the key already assigns tags, leave Worker network tags empty. xNaut does not add tag permissions or change your tailnet policy. |
| Enrollment fails | Check key expiry, revocation, tailnet and allowed tags. Save a replacement key if necessary. |
| Device approval required | Use a Pre-approved key for future workers; approve an already pending device in Tailscale. |
| Enrolled but repository unreachable | Check network access rules, DNS, firewall and server ports. The harness does not forcibly re-enroll an already running Tailscale connection. |
| Git or LFS authorization fails | Check the project's forge connection, deploy-key permissions and LFS support. Network enrollment does not fix repository authorization. |
